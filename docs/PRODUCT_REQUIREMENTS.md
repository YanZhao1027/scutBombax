# SCUT Bombax 产品需求草案

**文件位置：** `docs/PRODUCT_REQUIREMENTS.md`  
**版本：** Draft v0.2  
**定位：** 从宿舍余额查询工具升级为宿舍水电管理助手  
**状态：** 待确认，尚非开发指令

---

## 1. 产品目标

Bombax 不应只回答“现在还剩多少钱”，还应该帮助用户回答：

1. 最近电费消耗快不快？
2. 每天大约花多少钱？
3. 余额按照当前消耗速度还能用多久？
4. 今晚断网后还能不能看到上次余额？
5. 余额不足时，怎样最快到官方页面充值？

产品核心体验：

**查看余额 → 了解消耗 → 预测余量 → 及时充值。**

保留现有架构：

`Capacitor UI → Kotlin Native → OkHttp → SCUT`

不增加云端账户系统、第三方代理或远程数据库。

## 2. 已确认的项目约束

- DXC 登录及余额查询已经通过真机验证；GZIC 余额查询仍需对应校区用户验证。
- 一卡通 access token 实测有效期为约 70 天，refresh grant 不可用。
- Token 使用 Android Keystore 加密持久化；不保存一卡通密码。
- 用户手机在校外可能遇到一卡通服务 403，官方 SSL VPN 是允许的校外访问方式。
- 大学城宿舍网络通常在工作日相关的凌晨 00:06 断开；如果次日有放假安排则可能不断网。
- **宿舍电力不会因该网络断开安排而停止供应。** 余额归零预测不能被表述成停电预测。
- 已有常驻通知、单次在途查询约束，以及可选的非精确定时后台刷新。
- 非精确 Alarm 可能延迟，且在 Android 12+ 上无法保证从完全停止的状态启动前台服务。

以上约束必须在新功能中继续成立。

## 3. P0：本地余额历史

### 3.1 自动采样

每次成功查询余额后保存一条本地快照，包括：

| 字段 | 说明 |
|---|---|
| `id` | 本地记录 ID |
| `profile_id` | 本地身份分组标识 |
| `campus` | GZIC / DXC |
| `room` | 宿舍 |
| `recorded_at` | 实际查询成功时间 |
| `electric` | 电费余额 |
| `water` | 水费余额 |
| `ac` | 空调余额，可为空 |
| `units` | 各项原始单位 |
| `source` | manual / foreground / nightly / restore |

不保存学号明文、密码、token、cookie 或接口原始响应。

按本地用户、校区、宿舍和资源分别管理历史。换宿舍、切换不同用户时不能将两组数据合并。

### 3.2 存储

使用 Android 本地 SQLite，Room 可以作为实现方案。

要求：

- 完全离线可读。
- 默认不上传或同步到云端。
- 不依赖 WebView `localStorage` 存储余额历史。
- 相同查询结果的重复事件应合理去重。
- 退出登录默认保留历史；提供独立的“删除本地历史”操作。
- 历史文件不参与系统自动备份，除非日后明确设计用户可控的备份功能。

### 3.3 离线体验

学校接口无法访问时，首页仍显示最后一次成功查询的余额，并明确标注时间。

示例：

**电费余额 ¥23.40**  
最后更新：昨天 23:00  
当前无法连接校园一卡通，显示的是历史记录。

不能将历史读数冒充实时读数。

## 4. P0：晚间余额快照

### 4.1 用户需求

宿舍网络可能在凌晨 00:06 断开。用户希望提前记录余额，以便夜间离线查看和积累每日消耗数据。

### 4.2 时间安排

默认 **每天 23:00（北京时间）** 执行一次查询，不区分工作日和节假日。

原因：

- 距通常断网时间有足够缓冲。
- 每日采样时间一致，便于用量分析。
- 不需要引入不可靠的校历判断。

23:00 是计划时间，不是精确执行保证。继续使用现有非精确 Alarm 机制，界面显示“预计于 23:00 左右更新”。

### 4.3 实现约束

复用 `ScutRuntime`、`BalanceNoticeService` 和现有单线程查询队列。

- 用户主动开启，默认关闭。
- 继续遵守现有常驻通知依赖。
- 每天最多执行一次计划性快照。
- 不增加高频后台轮询。
- 不自动重新登录。
- 网络失败不连续重试。
- 后台任务错过时不批量补查。
- Android 系统未允许后台执行时，不能承诺快照必然成功。

当前 `DailySchedule` 的“开启后每隔 24 小时”逻辑需要调整为**按北京时间每天 23:00 计算下一次计划时间**，避免用户在下午开启后，每天下午自动刷新。

### 4.4 UI

设置名称：

**晚间余额快照**

说明：

“每天约 23:00 记录一次水电余额，供离线查看与用量统计。需要开启常驻通知，系统省电策略可能导致延迟或漏查。”

显示上一次成功快照时间和下一次计划时间。

## 5. P0：电费余额趋势图

这是本次产品迭代的主要视觉功能。

### 5.1 页面入口

首页保持轻量：

**电费余额 ¥23.40**  
近 7 天日均约 ¥2.10  
预计可用约 11 天

`查看电费趋势 →`

点击后进入电费详情页，不要把所有图表堆在首页。

### 5.2 主图：余额趋势

默认展示近 30 天电费余额折线图。

时间范围：

`7 天 | 30 天 | 90 天 | 全部`

图表要求：

- X 轴：日期。
- Y 轴：余额及其正确单位。
- 历史余额使用实线。
- 实际查询记录用数据点表示。
- 点按或拖动可查看具体时间和余额。
- 充值或余额显著增加的位置显示特殊标记。
- 缺测期间不能绘制伪造的采样点。
- 数据过密时允许视觉降采样，但不能修改底层记录。

交互示例：

**10 月 11 日 23:01**  
电费余额：¥21.30  
距上一次记录：减少 ¥2.10

### 5.3 充值标记

当余额较上一条记录显著增加时，标记为：

**疑似充值 / 余额调整**

不能直接宣称“充值成功 +¥50”，因为余额差值还可能受到期间消耗、后台入账或平台调整影响。

只有日后获得可靠的官方交易记录，才能展示精确充值金额。

### 5.4 预测线

当预测数据足够可靠时，在最后一条实际余额记录右侧显示：

- 一条较淡的虚线，代表预测趋势。
- 可选的浅色区间，代表预测不确定性。
- 预计余额归零的大致日期。

必须明显区分“实测”和“预测”。

预测不足以支持日期区间时，只展示“预计约 N 天”，不要生成虚假的高精度时间。

## 6. P1：每日消耗柱状图

在余额趋势下方增加：

**每日电费消耗**

目标是让用户直观看出哪几天消耗更高。

每根柱子代表一个日期或一个明确标注的观测区间。

统计规则：

- 若数据足够密集，可以计算对应日期的估算消耗。
- 若两个快照跨越多天，只能得出该区间的平均消耗速度，不能假装知道每一天的真实用量。
- 缺少数据时显示缺测，不自动填零。
- 充值跨越的区间不能直接使用余额下降量计算消耗。
- 所有由余额差推算出的消耗必须标注“估算”。

图表顶部可显示：

**近 7 天平均：约 ¥2.10 / 天**

只有前后两个统计窗口的数据都达到要求时，才显示“较上周增加 X%”。

## 7. P1：余额归零预测

### 7.1 基础算法

优先使用稳健统计，不引入 AI 模型。

处理步骤：

1. 读取同一宿舍、同一资源的近期余额快照。
2. 排除余额增加或异常调整所跨越的区间。
3. 计算各个有效观测区间的每日余额下降速度。
4. 优先根据近期数据计算稳健的日均消耗。
5. 用当前余额除以估算日均消耗，得到剩余天数。
6. 根据观测时长、样本数量和波动程度标记置信度。

第一版可以采用中位数等稳健方法，不需要复杂机器学习。

### 7.2 数据要求

建议起步标准：

- 至少 4 条有效快照。
- 覆盖至少 72 小时。
- 至少有 3 个有效消耗观测区间。
- 最近一次明显余额调整后数据不足时，暂停预测或降低可信度。

预测置信度分为：

`数据不足 / 低 / 中 / 高`

没有足够数据时不显示具体归零日期。

### 7.3 用户文案

推荐：

“按照最近的消耗速度，电费余额预计还能使用约 8～10 天。”

不允许：

“将在周五停电。”

不允许把余额归零与实际供电中断直接画等号。

## 8. P1：低余额提醒

支持用户设置提醒条件：

- 电费余额低于自定义金额。
- 预计剩余天数低于自定义天数。
- 完全关闭提醒。

提醒应基于最近一次可信查询和预测结果。

要求：

- 不重复推送同一风险等级。
- 数据过旧时明确说明提醒依据的是历史值。
- 用户充值后重新评估提醒条件。
- 不在查询失败时反复发送通知。
- 预测不可靠时只能按实际余额阈值提醒。

## 9. P1：官方充值入口

DXC 当前提供的候选官方充值入口：

`https://dfyc.utc.scut.edu.cn/sdms-weixin-pay/newWeixin/index.html`

在发布前必须使用真机验证该链接可以进入预期的官方充值流程，包括未登录、校园网和允许的 VPN 场景。

### 第一阶段

增加按钮：

**前往官方充值**

使用 Android `ACTION_VIEW` 或 Custom Tabs 打开官方页面。

说明：

“即将打开华工官方缴费页面，可能需要重新登录。”

安全要求：

- 不在 Bombax 内处理微信支付凭证。
- 不注入 OkHttp 的 TGC、locSession 或 JSESSIONID 到外部浏览器。
- 不自动创建订单或扣款。
- 不将支付结果仅凭浏览器返回行为判定为成功。
- GZIC 官方充值入口未验证前，不直接复用 DXC 链接。

### 充值后

用户返回 Bombax，可点击：

**我已充值，重新查询**

查询成功后更新本地余额历史与预测，若余额增加则显示“检测到余额增加”。

## 10. 图表视觉规范

Bombax 已采用极简、单栏、无阴影的页面设计。新图表必须延续该风格，而不是重新引入传统网页仪表盘。

### 布局

- 首页只放精简的余额与统计摘要。
- 图表放在独立详情视图。
- 不使用密集卡片墙。
- 不使用厚重阴影、装饰性渐变和多余图例。
- 手机宽度下不出现横向页面溢出。

### 颜色

- 电费：青绿或现有主强调色。
- 水费：蓝色。
- 空调费：橙色。
- 疑似充值：独立标记。
- 预测：低对比度虚线。

适配系统深色模式，避免仅靠颜色表达充值、预测或异常。

### 交互

- 支持手指拖动查看历史读数。
- Tooltip 不得超出屏幕。
- 时间范围切换应即时更新图表。
- 减少动画；尊重 `prefers-reduced-motion`。
- 数据点触控区域应足够大。
- 提供文字摘要或历史列表作为图表的无障碍替代。

### 实现

图表在 Capacitor 的 WebView 前端渲染；数据存储和统计计算位于本地 native 层。

Agent 可以评估按需引入 ECharts 或更轻量的替代方案。

禁止为图表增加 CDN、外部统计服务或服务器依赖。所有渲染资源应随 APK 离线打包。

## 11. 数据状态与异常处理

| 场景 | 产品行为 |
|---|---|
| 首次安装，无历史 | 展示空态，说明将在成功查询后开始记录 |
| 只有 1～2 个点 | 可以画点，不生成归零预测 |
| 网络断开 | 显示历史图表及最后成功查询时间 |
| 查询失败 | 不写入虚假快照 |
| 余额增加 | 标记疑似充值或调整，排除相关消耗区间 |
| 换宿舍 | 新建独立历史序列 |
| 单位改变 | 禁止直接合并计算 |
| 数据长期未更新 | 预测标记为过期或暂不可用 |
| 登录态失效 | 历史仍可查看，提示重新登录 |

## 13. 开发验收标准

Agent 完成每个版本时，应至少验证：

- 同一笔余额查询只写入合理数量的快照，不因 UI 与通知同时更新而重复写入。
- 历史数据在进程终止、重启后仍存在。
- 不同用户、校区、宿舍的数据不混合。
- 充值后的余额上涨不会被统计成负消耗。
- 缺失样本不会被绘制为真实每日消耗。
- 图表可在无网络条件下正常打开。
- 7 / 30 / 90 天切换正常，深浅色模式清晰可读。
- 23:00 计划不会因为实际执行延迟而逐日漂移。
- 后台查询仍经过唯一的 `ScutRuntime` 队列。
- 不记录敏感账号、Cookie、Token 或学校返回的私人信息。
- `pnpm build`、前端测试、JVM 测试、`assembleDebug` 均通过。
- 真机验收报告明确区分 `UNIT_TESTED` 和 `RUNTIME_VERIFIED`。

**特别要求：不为了图表或预测增加新的学校查询频率。** 所有统计能力都应优先利用原本的查询与每日快照产生的数据。

## 14. 产品设计总原则

**先让用户看明白，再让数据变丰富。**

Bombax 的首页应该在几秒内回答：

- 还剩多少钱？
- 最近每天大约用了多少？
- 估计还能撑几天？
- 需要充值时去哪儿？

图表负责解释这些数字，而不是用复杂图形给用户增加理解负担。

所有估算必须诚实地标明不确定性，所有历史读数必须带时间，所有充值操作最终都由用户在官方系统中确认。

## 15. 已确认决议（2026-10-08，用户答复）

| 决策点 | 结论 |
|---|---|
| 本地历史存储 | **手写 `SQLiteOpenHelper`**，不引入 Room/KSP；统计逻辑写成纯 Kotlin 模块，以便像现有 101 条 JVM 测试一样在主机上验证 |
| 趋势图渲染 | **手写 SVG 折线**，不打包 ECharts（CSP 为 `script-src 'self'`，禁止 CDN；打包图表库会让当前 5.9 KB HTML + 24.9 KB JS 的极简页面膨胀约十倍） |
| 交付节奏 | **先采样，后图表**。v0.2a = 原生历史写入 + 离线显示最后读数 + 23:00 快照改造；图表等历史积累到可验证的程度再做 |

### 15.1 单位口径（2026-10-08 已解除阻塞）

用户核对官方页面后确认：**DXC 本应用显示的电费余额单位是人民币元（¥），不是用电量（度/kWh）。**
标记为 `USER_VERIFIED` 而不是 `RUNTIME_VERIFIED` —— 接口本身不返回任何单位文本，
`resultObject.leftMoney` 是电与水两侧唯一的数值字段，界面上原先的"平台返回余额"是本项目自己写的标签。

统一口径：

| 项目 | 口径 |
|---|---|
| 余额趋势图 | 显示 ¥，纵轴为剩余金额 |
| 日均消耗 | 显示 ¥/天，含义是**估算的余额下降速度** |
| 归零预测 | 预测金额余额何时归零，**不预测停电时间** |
| 用电量 kWh | 另一项指标，官方对应字段尚未确认，本应用当前完全不读取 |
| 水费 | **单位仍未验证**，保持中性标签，不因电已确认而沿用 |
| GZIC | 单位需单独验证，不因 DXC 已确认而套用 |

取证探针：`DxcParser.resultKeys()` 在每次成功查询后把 `resultObject` 的**字段名**（仅名字，
值一律不外传，两条测试钉住）写入日志。下一次真机成功查询即可判断学校是否另外提供了带单位的
字段（例如电量或单价），从而以观测量代替猜测。

**恒久约束（用户特别强调）**：余额下降量只能当作**估算消费量**，不能当作实际缴费口径的消费金额。
跨越充值或余额调整的采样区间必须**排除或标记为未知**，不得计入日均，也不得记成负消耗。

### 15.2 与现有实现冲突、需要改动的两处

1. `java.time` 在 minSdk 24 不可用（API 26+）。按北京时间算下一次 23:00 用
   `Calendar` + `TimeZone.getTimeZone("Asia/Shanghai")`，不开 `coreLibraryDesugaring`。
2. `DailySchedule.nextTriggerAt` 原来的"锚点过期 → 60 秒后补一次"已移除，改为
   "错过即等下一个 23:00"；随之作废的是 24 小时间隔式的锚点自纠正逻辑与相关单测。
   日历算法下 §13 担心的逐日漂移由构造消除。

两处均已在 v0.2a 完成，设备验证见 `DEVICE_VERIFICATION.md` §14。

### 15.3 结构性要求

- 快照写入点必须在原生 `BillingRepository.fetchBills()` 成功处（唯一咽喉），
  不在 JS 的通知/渲染处，否则一次前台查询会被写两遍。
- `profile_id` 用 `SHA-256(campus|room)` 截断。它的作用是**防泄露到诊断输出**，不是匿名化：
  房间号取值空间很小、可枚举反推，且同一宿舍的不同用户会得到同一个键。当前单用户单机场景可接受；
  **在面向多用户或可导出的版本发布之前，必须改为 `HMAC(本机密钥, campus|room)`**
  （密钥由 Android Keystore 一次性生成），并同时决定序列身份属于宿舍还是账号。
  房间号本身与学号同级 —— 不进日志、不进仓库、不出现在验收材料里。
- 低余额提醒需要**独立通知通道**（现有 `bombax.balance` 是 `IMPORTANCE_LOW` 的常驻状态条，
  不响铃、无角标），并且只复用快照得到的那一次查询结果。
